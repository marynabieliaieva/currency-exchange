## Findings

### Stage 1 (spec/AC compliance — blocking)

1. **Amend ceiling bound is wrong** — `backend/src/main/java/com/currencyexchange/orderentry/repository/OrderMongoOperations.java:81`,
   `service/OrderService.java:89-92`. AC: AC-06/AC-07/AC-12, `contracts/openapi.yaml:313`. Guards
   against the order's *current* `remainingAmount` instead of `(amount − already-filled)`; after any
   downward amend the allowed range collapses monotonically and a legitimate upward amend is wrongly
   rejected, with the 409 message quoting the wrong bound.
   **Verdict: Fix now.**

2. **No test distinguishes the two amend-ceiling interpretations** —
   `backend/src/test/java/com/currencyexchange/orderentry/repository/OrderMongoOperationsIntegrationTest.java:122-133`.
   AC: AC-12. The only range fixture (remaining=600, filled=400 on a 1000 order) makes current-remaining
   and (amount−filled) numerically identical, so it passes under either interpretation and masks
   finding 1.
   **Verdict: Fix now.**

3. **AC-11 read-path fallback missing** — `backend/src/main/java/com/currencyexchange/orderentry/service/OrderService.java:45-52`.
   AC: AC-11. The null→amount fallback is applied only inside the write guards
   (`$ifNull` in `OrderMongoOperations.java:99-100`), not in `listOrders`/`getOrder`, so a legacy order
   serializes `remainingAmount: null` on the wire — contradicting `openapi.yaml:269-276`'s "never null"
   guarantee — and the UI renders blank cells in `ManageOrdersList.tsx`, `FillDialog.tsx`, and
   `CancelForfeitureDialog.tsx`.
   **Verdict: Fix now.**

4. **Sub-scale fill recorded as a permanent zero-value entry** —
   `backend/src/main/java/com/currencyexchange/orderentry/service/OrderService.java:62-65,104-106`.
   AC: AC-04. Positivity is checked *before* scale-8 normalization; an amount like `0.000000001`
   passes `> 0`, normalizes to `0E-8`, and is still appended to the fill trail as an unreversible
   junk entry (no correction path exists per spec §3).
   **Verdict: Fix now.**

5. **Empty PATCH body causes a 500, not the contract's 400** —
   `backend/src/main/java/com/currencyexchange/orderentry/dto/AmendRequest.java:7-28`. AC: AC-06.
   `openapi.yaml:302-304` declares `minProperties: 1`; nothing enforces "at least one field" before
   the update reaches Mongo, which fails to parse an empty `$set` — unhandled `MongoCommandException`
   instead of a validation 400.
   **Verdict: Fix now.**

6. **Malformed order id returns 500 instead of the contract's 404** —
   `backend/src/main/java/com/currencyexchange/orderentry/repository/OrderMongoOperations.java:95`
   (`new ObjectId(id)`). `openapi.yaml:106,141-142,196` specify 404. DELETE/PATCH/fill throw an
   unhandled `IllegalArgumentException`; only GET (via `findById`) 404s correctly today.
   **Verdict: Fix now.**

7. **AC-15 routing test never renders the real route table** — `frontend/src/App.test.tsx:14-27,36-42,51-57`.
   Each test re-declares its own `<Routes>` instead of mounting `App.tsx`'s actual table (including
   its catch-all), so a wrong path in `App.tsx` would still pass — ADR-0002's decision is effectively
   unverified.
   **Verdict: Fix now.**

8. **Missing success banner on Manage Orders after cancel/fill/amend** —
   `frontend/src/pages/ManageOrdersPage.tsx:43-46`. AC: AC-01/AC-02/AC-03/AC-06 ("confirms to the
   Trader" / "confirms the new values"); `screens.md` names `InlineStatusBanner` as NEW for exactly
   this reason. Only the mutated row changes — no confirmation is shown, unlike the entry page
   (`OrderEntryPage.tsx:17`).
   **Verdict: Fix now.**

9. **AC-02's "remaining amount left unchanged" has no deterministic backend test** —
   `backend/src/test/java/com/currencyexchange/orderentry/repository/OrderMongoOperationsIntegrationTest.java:36-56`
   cancels only fill-free orders. The only assertion of the invariant lives in a race-dependent
   concurrency-test branch (`service/OrderConcurrencyIT.java:91-96`) that may not execute on a given
   run.
   **Verdict: Fix now.**

### Stage 2 (quality — usually non-blocking)

10. **AC-12 frontend test mocks a fictional error shape** —
    `frontend/src/pages/ManageOrdersPage.test.tsx:241-247`. Uses `(400, "order.invalid_amend")`;
    the real contract (and `GlobalExceptionHandler.java:47-51`) is `(409, "order.amend_out_of_range")`
    with different wording. Passes against a contract the backend doesn't implement.
    **Verdict: Fix now.**

11. **`AmendRequest.remainingAmount` carries no bean validation** —
    `backend/src/main/java/com/currencyexchange/orderentry/dto/AmendRequest.java:9-12`. AC-12,
    `openapi.yaml:309-313` (`exclusiveMinimum: 0`). Unlike `triggerPrice`, a negative value bypasses
    the DTO layer and surfaces as a 409 range-rejection rather than the 400 the schema implies —
    inconsistent with the fill path.
    **Verdict: Fix now.**
