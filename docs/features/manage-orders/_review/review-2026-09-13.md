## Findings — original 11 (2026-09-12), all closed

1. Amend ceiling now uses `(amount − already-filled)` via a `$reduce` over `fillEvents`
   (`OrderMongoOperations.java`), not the current `remainingAmount` — verified with a fixture where
   the two interpretations diverge (prior downward amend + fills recorded).
2. The masking test fixture was replaced with one that discriminates the two interpretations.
3. AC-11 read-path fallback applied in `listOrders`/`getOrder`/`cancelOrder`/`amendOrder` (see also
   finding 12 below, closed in the second pass).
4. Fill positivity is checked after scale-8 normalization — a sub-scale amount can no longer be
   recorded as a permanent zero-value fill event.
5. `AmendRequest` now has an `@AssertTrue` requiring at least one field present — an empty PATCH
   body 400s instead of 500ing on Mongo's `$set` of an empty document.
6. `OrderMongoOperations.tryCancel/tryFill/tryAmend` guard malformed ids via `ObjectId.isValid`
   before constructing a filter — cancel/fill/amend now 404 consistently with GET instead of 500ing.
7. `App.tsx`'s route table was extracted to `AppRoutes.tsx`; `App.test.tsx` now mounts it directly
   (including a new catch-all-route test) instead of a re-declared copy.
8. `ManageOrdersPage.tsx` now shows an inline confirmation banner after cancel/fill/amend, matching
   the entry page's existing pattern.
9. AC-02's "remaining amount left unchanged" now has a deterministic integration test, independent
   of the race-timing concurrency test.
10. The amend-rejection frontend test now mocks the contract's real `(409, order.amend_out_of_range)`
    shape instead of a fictional `(400, order.invalid_amend)` one.
11. `AmendRequest.remainingAmount` now has `@DecimalMin` bean validation, matching `triggerPrice`.

## Findings — residual from the first re-review (2026-09-12→13), all closed

12. **[stage-1, closed]** `OrderService.amendOrder` now wraps its return in
    `withRemainingAmountFallback` — a price-only amend on a legacy order no longer responds with
    `remainingAmount: null`. Verified by `OrderServiceTest.amendOrderAppliesRemainingAmountFallbackWhenPriceOnlyAmendLeavesItUnset`
    and `OrderServiceLegacyDocumentIT.amendOrderOnALegacyDocumentStillReturnsANonNullRemainingAmount`.
13. **[stage-2, closed]** Added `OrderServiceLegacyDocumentIT`, which inserts a raw Mongo document
    with `remainingAmount`/`fillEvents` genuinely absent (not null/empty) and proves `getOrder`/
    `amendOrder` handle it.
14. **[stage-2, closed]** Split the frontend amend-to-zero test (400, bean validation, no `code`)
    from the amend-above-max test (409, `order.amend_out_of_range`) — they are different branches
    and were wrongly sharing one mocked response shape. Added the equivalent `0`-exactly case to
    `OrderControllerTest`.
15. **[stage-2, closed]** Each dialog (`CancelDialog`/`CancelForfeitureDialog`/`FillDialog`/
    `AmendDialog`) now calls an `onRejected` callback wired to `ManageOrdersPage.refreshOrders` on
    any rejection, so a row that lost an AC-10/AC-13 race no longer shows stale PENDING actions
    after the error is dismissed. Verified with a test asserting two distinct `listOrders` responses
    and the row updating to `CANCELLED`.
16. **[stage-2, closed]** `docs/features/manage-orders/contracts/` (openapi.yaml +
    api-sync-report.md) is now committed on the branch.

## Non-blocking observation (second re-review)

`onRejected` fires on every dialog rejection, not only AC-10/AC-13 race losses (e.g. also on a
plain AC-04/AC-12 validation rejection). Harmless — an idempotent extra `GET`, dialog stays open
either way — noted for awareness, not a gate item.
